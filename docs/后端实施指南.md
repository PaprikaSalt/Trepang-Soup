# Trepang Soup 后端实施指南

本文用于在 WSL Ubuntu 24.04 中实现 Trepang Soup 后端，随后部署到 Ubuntu 24.04 x86-64 公网服务器。首版不使用 Docker，不持久化完成对局，不提供网页端。

## 1. 后端职责

服务端负责：

- 创建、加入、关闭和恢复好友房间。
- 维护最多 20 人的在线状态及房主转移。
- 串行处理正式问题队列。
- 广播讨论、问答、提示和系统事件。
- 保护汤底、关键事实与 DeepSeek API Key。
- 调用 DeepSeek完成题目生成、逻辑检查、主持回答、提示、结案和总结。
- 管理私人题库和近期抽题记录。
- 对所有AI结构化输出进行验证。

服务端不负责：

- 注册、登录和长期玩家身份。
- 保存昵称、讨论、问答或完成对局历史。
- 排行榜、个人积分和跨设备同步。
- 音频、文件上传或网页界面。

## 2. 推荐技术

- Python 3.12 或 Ubuntu 24.04 默认受支持的稳定版本
- FastAPI
- Uvicorn
- Pydantic / pydantic-settings
- httpx
- websockets
- SQLAlchemy 2 + aiosqlite
- Alembic
- pwdlib[argon2] 或 argon2-cffi
- pytest / pytest-asyncio
- ruff
- mypy

所有依赖应锁定版本。开始后端实现时再根据 WSL 中可用版本生成锁文件，不在本文硬编码未来可能过期的精确版本。

## 4. WSL 初始化

从 Windows 把整个项目复制到 WSL 的 Linux 文件系统，例如：

```bash
mkdir -p ~/projects
cp -r /mnt/c/Users/PaprikaSalt/Desktop/Trepang* ~/projects/trepang-soup
cd ~/projects/trepang-soup
```

不要长期直接在 `/mnt/c` 下运行 Python虚拟环境和文件监听器，Linux 文件系统性能与权限行为更稳定。

安装基础工具：

```bash
sudo apt update
sudo apt install -y python3 python3-venv python3-pip sqlite3 build-essential
```

创建环境：

```bash
cd server
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
```

## 6. 内存房间模型

每个房间由一个 `RoomActor` 或一个受单独 `asyncio.Lock` 保护的对象管理。

建议字段：

```text
room_id
invite_code
stage
source
difficulty
style
host_player_id
players
puzzle_surface
puzzle_truth
key_facts
questions
timeline
discussions
hint_count
event_sequence
recent_events
processed_command_ids
created_at
started_at
settled_at
question_worker_task
room_lock
```

必须满足：

- 对同一房间的命令变更按顺序执行。
- 正式问题只能由一个队列工作器消费。
- WebSocket广播不能持有房间写锁等待慢客户端。
- 先在锁内创建事件，再把事件副本放到每个连接的发送队列。
- 单个慢连接的发送队列达到上限时断开该连接，不能拖慢全房间。

## 7. 房间管理器

`RoomManager` 维护：

- `room_id -> Room`
- `invite_code -> room_id`
- `session_token_hash -> player session`
- 后台清理任务

创建邀请码：

- 字符集建议 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`
- 使用 `secrets.choice`
- 冲突时重试
- 邀请码只在房间存活期间有效

房间销毁条件：

- 房主主动关闭。
- 结算事件已经向当前在线客户端发送，短暂宽限后销毁。
- 所有玩家离线且超过空闲时间。
- 服务进程退出或重启。

销毁时取消：

- 问题队列任务
- 正在进行的 DeepSeek调用
- 房主转移计时任务
- 所有 WebSocket发送任务

## 8. 玩家会话

首次创建或加入时：

1. 生成 `player_id`。
2. 生成高熵 `session_token`。
3. 服务端只在内存中保存令牌哈希。
4. 客户端本地保存原始令牌。
5. 重连成功后轮换令牌。

同一个昵称不能在同一房间重复。比较时应：

- 去除首尾空白。
- Unicode规范化。
- 建议忽略英文字母大小写。

服务器重启后所有玩家会话自然失效，符合首版“不恢复活跃房间”的要求。

## 9. 正式问题队列

### 提交

1. 验证玩家在线、房间正在游戏、内容长度合法。
2. 在房间锁内创建 `queued` 问题。
3. 递增事件序号并广播 `question.queued`。
4. 唤醒队列工作器。

### 撤回

仅当：

- 请求者是提交者。
- 问题状态仍为 `queued`。

一旦状态进入 `thinking`，拒绝撤回并返回 `QUESTION_ALREADY_PROCESSING`。

### 消费

队列工作器循环：

1. 在锁内选择最早的 `queued` 问题。
2. 改为 `thinking` 并广播。
3. 复制AI所需的不可变上下文后释放锁。
4. 调用 DeepSeek。
5. 验证响应结构。
6. 在锁内提交 `answered` 或 `failed`。
7. 广播结果并继续下一题。

DeepSeek失败重试：

- 网络错误、429、5xx：最多两次退避重试。
- JSON错误：使用同一上下文执行一次格式修复请求。
- 内容策略拒绝或连续失败：广播 `question.failed`，不要让整个队列永久阻塞。

## 10. DeepSeek客户端

使用单例 `httpx.AsyncClient`：

- 连接复用。
- 全局并发限制。
- 单请求总超时。
- 请求 ID 写入结构化日志。
- 不记录完整提示词和汤底。

请求入口使用 DeepSeek Chat Completions API。所有结果都应要求结构化 JSON，并再次由 Pydantic 验证。不能相信模型生成的工具参数天然有效。

### 主持回答结构

```json
{
  "answerType": "yes",
  "answer": "是。灯光确实在传递信息。",
  "confirmedFact": "灯光是主动产生的信号",
  "newFactStrength": "small",
  "safetyFlags": []
}
```

约束：

- `answerType`必须为 `yes/no/irrelevant/partial`。
- `answer`建议不超过 80 个汉字。
- 不得透露玩家尚未推出的完整关键真相。
- `confirmedFact`只在本次回答确实确认事实时填写。

## 11. AI上下文

主持上下文分为四层：

1. 固定主持规则。
2. 当前汤面、汤底和关键事实。
3. 已回答的正式问题及结构化确认事实。
4. 当前玩家问题。

普通问答不包含讨论区内容。这样玩家的猜测不会被AI误当作已确认事实。

公共提示可以读取：

- 正式问答。
- 已确认事实。
- 使用提示次数。

默认不读取讨论区。如果未来希望提示能理解玩家卡在哪里，可只加入最近有限数量的讨论，并明确标记为“未经确认的玩家猜测”。

## 12. 提示词设计

### 固定主持规则

```text
你是好友海龟汤房间的主持人。
你的目标是帮助玩家通过是非问题自行还原真相，而不是替玩家讲出答案。

规则：
1. 只依据汤底与关键事实判断。
2. 回答类型只能是 yes、no、irrelevant、partial。
3. 回答必须简短，以明确判断开头。
4. 可以偶尔带一点温和的损友感，但不能侮辱、讽刺玩家身份或根据昵称做人身化发挥。
5. 不得因为玩家猜测而改变汤底。
6. 不得在普通回答中主动透露尚未问到的关键事实。
7. 输出必须符合给定 JSON Schema。
```

### 公共提示规则

```text
请根据正式问答梳理：
- 已确认事实
- 已排除方向
- 当前明显矛盾
- 一个不会直接揭底的小提示

不要给出完整答案。提示必须让新手能够继续提出问题，但仍保留最后一步推理。
```

### 结案判断规则

输出：

```json
{
  "result": "correct",
  "missingFacts": [],
  "feedback": "",
  "confidence": 0.94
}
```

`result`：

- `correct`
- `close`
- `wrong`

服务端不能只依赖模型自报置信度。至少检查：

- `correct` 时所有必要关键事实是否被覆盖。
- `close` 时 `missingFacts` 是否来自真实关键事实列表。
- `feedback` 是否意外泄露完整答案。

## 13. AI生成题目

房主选择：

难度：

- `beginner`
- `standard`
- `hard`

风格：

- `light_daily`
- `classic_mystery`
- `dark_thriller`
- `absurd_humor`

生成结构：

```json
{
  "title": "内部展示标题",
  "surface": "汤面",
  "truth": "完整汤底",
  "keyFacts": [
    "必须推理出的事实"
  ],
  "assumptions": [],
  "contentWarnings": [],
  "difficultyRationale": "为什么符合所选难度"
}
```

质量检查使用第二次独立请求：

- 汤面与汤底是否矛盾。
- 关键行为是否有合理动机。
- 玩家能否通过是非问题推到答案。
- 是否依赖冷门专业知识、纯谐音或不可验证设定。
- 是否符合风格和内容边界。
- 是否存在多个同等合理但未被汤底覆盖的答案。

检查失败则最多重新生成两次。连续失败时向房主返回可重试错误，不使用低质量题目开局。

## 14. 私人题库

SQLite表：

### `puzzles`

```text
id TEXT PRIMARY KEY
title TEXT NOT NULL
surface TEXT NOT NULL
truth TEXT NOT NULL
key_facts_json TEXT NOT NULL
active INTEGER NOT NULL DEFAULT 1
created_at INTEGER NOT NULL
updated_at INTEGER NOT NULL
```

### `puzzle_selections`

```text
id INTEGER PRIMARY KEY AUTOINCREMENT
puzzle_id TEXT NOT NULL
selected_at INTEGER NOT NULL
room_fingerprint TEXT NULL
```

首版不需要保存真实 `room_id` 或昵称。`room_fingerprint` 可以省略，仅保留全局抽取顺序。

随机规则：

1. 查询所有启用题目。
2. 排除最近 10 个不同题目 ID。
3. 如果候选为空，选择最久未出现的启用题目。
4. 选择后立即写入 `puzzle_selections`。
5. 定期只保留足够计算近期窗口的记录。

## 15. 本地历史与服务端清除

服务端完成结算时：

1. 生成 `game.settled`。
2. 把事件放入每个在线连接的发送队列。
3. 等待短暂确认窗口。
4. 删除房间对象、会话和事件缓存。
5. 不把任何对局内容写入 SQLite。

客户端收到 `game.settled` 后，把已接收的房间事件、汤底和结算保存到本机 SQLite。

需要接受的限制：离线玩家没有收到结算事件时，服务端销毁后无法恢复完整本地记录。

## 16. 管理员认证

因为用户暂时接受未加密公网 IP：

- 管理员密码必须专用且随机。
- 登录前获取一次性挑战。
- 响应包含挑战 ID、时间戳和 HMAC。
- 挑战只能使用一次并在 60 秒内过期。
- 管理令牌有效期建议 15 分钟。
- 连续失败需要短暂限速。

但必须在文档和日志中明确：没有 TLS 时仍可遭受中间人窃听、重放或篡改。挑战响应不是 HTTPS 的替代品。

## 17. 日志

推荐 JSON 结构化日志字段：

```text
timestamp
level
component
request_id
room_id_hash
player_id_hash
command_type
event_id
ai_latency_ms
ai_attempt
error_code
```

不得记录：

- API Key
- 管理员密码或挑战响应
- 会话令牌
- 完整汤底
- 完整讨论和问答内容

生产日志可以记录长度、计数和不可逆短哈希。

## 18. 测试计划

### 单元测试

- 邀请码字符集和冲突重试。
- 昵称规范化和重复判断。
- 房主转移顺序。
- 问题状态机和撤回权限。
- 最近 10 道题排除算法。
- AI输出Schema校验。
- 评分扣分和最低分保护。

### 并发测试

- 20 人同时加入。
- 多人同时提交问题，顺序与接收时间一致。
- `thinking` 状态后撤回被拒绝。
- 同一 `commandId` 重复发送不产生重复问题。
- 慢客户端不阻塞全房间。
- 房主断线后只有一次转移事件。

### 契约测试

- 每个事件均符合 `通信协议-v1.md`。
- 客户端可以忽略新增可选字段。
- 快照不包含汤底。
- `game.settled` 才首次向普通客户端暴露汤底。

### AI测试

准备固定测试题目和问题集，验证：

- 判断不自相矛盾。
- 不提前泄底。
- 提示逐步推进。
- 接近正确时只指出缺失事实。
- 赛后奖项不冒犯玩家。

## 19. WSL联调

服务端启动：

```bash
source .venv/bin/activate
uvicorn app.main:app --host 0.0.0.0 --port 8787 --reload
```

在 Windows PowerShell 获取 WSL 地址：

```powershell
wsl hostname -I
```

客户端开发配置指向：

```text
http://<WSL-IP>:8787
ws://<WSL-IP>:8787
```

如果 Windows 不能访问：

- 检查 Uvicorn 是否监听 `0.0.0.0`。
- 检查 WSL防火墙。
- 检查 Windows 到 WSL 的网络模式。
- 先用浏览器或 `curl` 验证 `/health`。

不要在问题排查阶段把 DeepSeek Key写入客户端。

## 20. 公网服务器部署

服务器准备：

```bash
sudo apt update
sudo apt install -y python3 python3-venv sqlite3
sudo useradd --system --create-home --shell /usr/sbin/nologin trepang
sudo mkdir -p /opt/trepang-soup /var/lib/trepang-soup
sudo chown -R trepang:trepang /opt/trepang-soup /var/lib/trepang-soup
```

推荐 systemd 单元：

```ini
[Unit]
Description=Trepang Soup API
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=trepang
Group=trepang
WorkingDirectory=/opt/trepang-soup/server
EnvironmentFile=/opt/trepang-soup/server/.env
ExecStart=/opt/trepang-soup/server/.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8787
Restart=on-failure
RestartSec=3
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/lib/trepang-soup

[Install]
WantedBy=multi-user.target
```

启动：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now trepang-soup
sudo systemctl status trepang-soup
```

防火墙：

```bash
sudo ufw allow 8787/tcp
```

首版直接开放 Uvicorn 端口只适合小范围实验。之后切换 HTTPS 时，应在前面增加 Caddy 或 Nginx，并只让反向代理暴露公网端口。

## 22. 后端完成定义

满足以下条件才视为首版后端完成：

- 两台以上 Windows客户端可通过 WSL或公网 IP加入同一房间。
- 20 人加入不破坏房间状态。
- 正式问题严格串行，撤回规则正确。
- DeepSeek短暂失败不会卡死问题队列。
- 中途加入与断线重连得到一致快照。
- 汤底在结算前从不发送给普通客户端。
- 完成对局不会写入服务器数据库。
- 私人题库可增删改、导入导出并避免近期重复。
- 服务重启后旧房间明确失效。
- systemd可自动拉起服务。
- 客户端完整流程与模拟模式表现一致。
