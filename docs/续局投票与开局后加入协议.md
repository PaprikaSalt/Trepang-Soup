# 续局投票与开局后加入协议

本文记录客户端与服务端共同实现的状态机和验收约束。客户端已完成协议类型、状态归并和结算
页交互，服务端已实现本文所列命令、事件、快照、异步换题和清理规则。

## 1. 当前结论

### 开局后加入

现有后端已经允许在 `playing` 阶段调用 `POST /api/v1/rooms/join`，新玩家首次 WebSocket
握手也会收到包含 `stage: "playing"`、当前玩家、汤面、问答、时间线和聊天室内容的完整
`room.snapshot`。

昨天表现为“无法加入”的根因在客户端：加入完成后无条件进入大厅，而服务端快照在路由切换
前已经把阶段更新为 `playing`，大厅页面随后建立的监听不会再收到变化。客户端已改为在
admission 完成后按权威快照阶段导航，并补充了服务端单元回归测试。

服务端继续保留以下规则，不需要为开局后加入新增接口：

- `lobby`、`playing` 和 `settlement` 的投票阶段允许加入；
- `closed` 必须拒绝加入；
- `playing` 快照必须包含当前轮的 `puzzleSurface`、全部公开问答、时间线和聊天室；
- 加入成功后继续广播 `player.joined`，连接成功后广播 `player.online_changed`；
- 结算后的完整汤底只能在 `settlement` 快照中发送。

## 2. 续局投票目标

- 房间号、房间 ID、成员身份、房主和 WebSocket 会话保持不变；
- 每位仍在房间中的成员都必须明确同意，才开始准备下一局；
- 投票期间允许撤回同意；
- 玩家点击“退出房间”时发送现有 `room.leave`，离开后不再计入本轮投票；
- 下一局沿用房间最初的题目来源；AI 房间沿用难度和风格，私人题库继续随机抽取并避免
  近期重复；
- 新题生成期间不广播未完成题目，也不泄露汤底、关键事实或模型提示词；
- 新一局开始时清空上一局的问答、提示、聊天室、时间线和结算状态，但保留本地历史记录。

## 3. 协议扩展

协议版本继续使用 `1`。新增字段均为可选，旧客户端会忽略未知事件；支持续局的服务端在结算
后发送 `rematch`，当前客户端据此显示投票区。

### 3.1 客户端命令

新增 `rematch.vote`，仅允许在 `settlement` 且 `rematch.status == "voting"` 时执行。

```json
{
  "agree": true
}
```

- `agree: true`：加入同意集合；
- `agree: false`：撤回同意；
- 同一 `commandId` 必须幂等；
- 无论是否达到全员同意，都先广播一次由该命令引起的 `rematch.updated`。

### 3.2 投票状态

```json
{
  "status": "voting",
  "eligiblePlayerIds": [
    "player_host",
    "player_guest"
  ],
  "acceptedPlayerIds": [
    "player_host"
  ]
}
```

`status` 仅有：

- `voting`
- `generating`

`eligiblePlayerIds` 必须由服务端生成，客户端不得提交或覆盖。

### 3.3 服务端事件

#### `rematch.updated`

载荷直接使用完整投票状态，不套额外的 `rematch` 字段。以下情况必须广播：

- `game.settled` 之后初始化空投票；
- 玩家同意或撤回；
- 投票阶段有玩家加入或离开。

#### `rematch.generating`

达到全员同意后广播，载荷仍是完整投票状态，但 `status` 为 `generating`。随后在后台准备
下一题，不得在持有房间锁时等待 DeepSeek 或数据库。

#### `room.restarted`

下一题准备成功后广播：

```json
{
  "roundNumber": 2,
  "startedAt": 1785480000000,
  "puzzleSurface": {
    "id": "runtime-puzzle-id-2",
    "title": "仅供结算和历史使用的内部标题",
    "surface": "新的汤面正文"
  }
}
```

客户端收到后会清空本轮临时状态，将阶段切为 `playing` 并进入原房间的游戏页。标题仍可留在
协议中供结算和本地历史使用，但游戏界面不会显示。

#### `rematch.failed`

生成或抽题失败时广播：

```json
{
  "rematch": {
    "status": "voting",
    "eligiblePlayerIds": [
      "player_host",
      "player_guest"
    ],
    "acceptedPlayerIds": []
  },
  "error": {
    "code": "AI_TEMPORARILY_UNAVAILABLE",
    "message": "下一碗汤暂时没有准备好，请重新投票。",
    "retryable": true,
    "details": {}
  }
}
```

失败后回到投票状态并清空同意集合，避免恢复网络后自动重复扣费生成。

### 3.4 房间快照

`room` 增加可选字段：

```json
{
  "roundNumber": 1
}
```

顶层增加可选字段：

```json
{
  "rematch": {
    "status": "voting",
    "eligiblePlayerIds": [],
    "acceptedPlayerIds": []
  }
}
```

- 仅在 `settlement` 阶段发送 `rematch`；
- 重连必须恢复当前投票和生成状态；
- `playing` 阶段不发送上一轮 `settlement` 或 `rematch`。

## 4. 服务端状态规则

### 4.1 投票成员

- `game.settled` 后，以当时 `room.players` 的全部成员初始化 `eligiblePlayerIds`；
- 成员离线但没有执行 `room.leave` 时仍属于房间，仍需投票；
- 投票期间加入的新成员立即加入 `eligiblePlayerIds`；
- 成员离开或被踢出后，从 eligible 和 accepted 中同时删除；
- 每次成员集合变化后重新判断是否全员同意；
- `eligiblePlayerIds` 非空且与 `acceptedPlayerIds` 集合相等时进入生成状态。

### 4.2 生成期间

- `rematch.status == "generating"` 时冻结投票；
- 生成期间暂时拒绝新的 admission，建议返回 HTTP `409`，错误码
  `REMATCH_IN_PROGRESS`；
- 已有成员仍可断线重连并收到 `generating` 快照；
- 玩家主动离开不取消正在进行的生成；
- 使用 generation ID 或目标 `roundNumber` 防止迟到的异步结果覆盖已经关闭的房间。

### 4.3 新一局重置

成功生成下一题后，在同一个房间对象内原子完成：

1. `roundNumber += 1`；
2. 替换 `puzzle`；
3. `stage = playing`；
4. 更新 `started_at`，清空 `settled_at`；
5. 清空 `questions`、`discussions`、本轮时间线和 `hint_count`；
6. 清空 `settlement`、投票状态和正在处理的结论；
7. 停止或作废上一轮尚未完成的问答、提示和结论后台任务；
8. 保留 players、host、invite code、sessions、连接邮箱和递增的 `event_sequence`；
9. 广播 `room.restarted`。

`event_sequence` 不得归零，否则已连接客户端会误判事件重复或缺口。

## 5. 清理策略必须修改

当前 `Room.cleanup_due()` 把 `settled_at` 当作终态，并通过
`room_settlement_grace_seconds` 在结算后约 5 秒删除房间。这与投票续局冲突。

后端应改为：

- 只有 `closed_at` 使用短暂 delivery grace 后清理；
- `settlement` 不再是终态；
- 结算或投票阶段全部玩家离线时，沿用 `room_idle_seconds` 清理；
- 任意投票、加入、离开、重连或生成状态变化都刷新 `last_activity_at`；
- 房主关闭房间仍立即进入 `closed`，取消生成任务并按 grace 清理。

## 6. 题目选择

- AI 房间：使用房间保存的原 difficulty 和 style 再调用生成与质量审查；
- 私人题库：再次调用 repository 的随机选择逻辑；
- 近期去重必须包含同一房间刚结束的题目；
- 选择失败不得破坏上一局结算页和投票成员信息；
- 不要把 DeepSeek API Key、系统提示、汤底或关键事实写入任何新事件。

## 7. 必须补充的测试

### 开局后加入

- `playing` 阶段 admission 成功；
- 新玩家初始快照的阶段是 `playing`；
- 快照包含汤面和已有公开进度，不包含汤底与关键事实；
- 原成员收到 `player.joined`，新成员可立即发讨论和正式问题。

### 投票

- 结算后广播空的 `rematch.updated`；
- 单人同意不会开局；
- 重复 command ID 不重复计票或生成；
- 撤回同意有效；
- 加入、离开、踢出会正确更新 eligible 和 accepted；
- 离线但未离开的成员仍会阻止全员通过；
- 最后一票只启动一次生成。

### 新一局

- AI 和私人题库各自生成或抽取新题；
- `room.restarted` 后保留房间号、成员、房主、会话和事件序号；
- 上一局的问答、提示、讨论、结算和汤底不进入新局快照；
- 新局问题只使用新汤底；
- 生成失败回到空投票，不关闭房间；
- 生成中关闭房间不会被迟到结果重新打开；
- 结算房间不会再被 5 秒清理，全部离线后仍按 idle 策略回收。

## 8. 联调验收

1. 两名玩家进入房间并开局；
2. 第三名玩家在开局后使用邀请码加入，直接进入游戏页；
3. 第三名玩家能看到已有公开问答并能正常发问；
4. 结束本局，三人结算页都显示 `0 / 3`；
5. 两人同意时保持结算页；
6. 第三人同意后全部客户端显示准备中；
7. 新题完成后三人自动进入同一个房间号的下一局；
8. 新局无上一局问题、提示、讨论或汤底残留；
9. 再次结束后，本机历史中能分别看到两局记录；
10. 一名玩家退出后，剩余成员投票不再等待已退出玩家。
